Usage: __ME__ ACTION [ARGS] [-j|--json]
       __ME__ ACTION --help   (or: help ACTION)
       __ME__                 open the TUI in a terminal

-j, --json prints JSON instead of the human-readable output; every action
but ssh takes it (scripts and the MCP server use it).

Subcommands accept unique prefixes. ls, nodes and instances are aliases
for machines. info aliases inspect and flavors aliases profiles.

Actions:
  start NAME [--name JOB] [--workdir DIR] -- CMD
                       start a registered job
  jobs [NAME] [-w]     list registered jobs across workers or on one worker
  ps [NAME] [--long]   show processes of running jobs on one or all workers
  logs [NAME [JOB]] [--lines N] [--follow] [--no-events] [--quiet]
       [--topic REGEX] [--agent REGEX]
                       show logs; follow includes lifecycle events and a worker
                       count status line (every 5 min, once when none) by default
  events [-w|--watch] [--topic REGEX] [--agent REGEX]
                       list and follow worker and job lifecycle events
  profiles [NAME] [-o wide]
                       list worker profiles and optionally their image details
  up [--ttl 2h] [--flavor s1.xlarge] [--disk 150] [--topic TEXT]
     [--no-nix-cache] [--no-nix-auth] [--no-niks3-token] [--ssh [-l USER]]
                       create a worker and wait until it is ready
  image create [--flake FLAKE] [--upload] | image upload --name NAME IMAGE
                       build or upload a worker disk image
  machines [-o json|wide | --wide] [--watch [-n SECONDS]]
                       list all workers (ad-hoc and nixbot's pool)
  exec [UP_OPTIONS] [--sync SRC[:DEST]] [--fetch REMOTE[:LOCAL]] [--keep] -- CMD
                       one-shot: create a worker, run CMD, delete the worker
  inspect NAME [--boot]
                       show everything known about a worker
  down NAME            delete a worker
  prune [NAME...] [--all] [-y] [-n]
                       delete several ad-hoc workers (default: your own)
  extend NAME --ttl D  move the expiry to now + D (max 24h)
  topic NAME TEXT...   change what the worker is for (shown by ls)
  ssh [-l USER | USER@]NAME [SSH_ARGS...]
                       ssh to the worker (pinned host key); options such as
                       -L/-A and a command go straight to ssh
  ssh --create [-l USER] [UP_OPTIONS]
                       create a worker and log in (same as up --ssh)
  sync [USER@]NAME SRC [DEST]
                       rsync SRC to the worker (default ~/SRC basename)
  cp [USER@]NAME:REMOTE LOCAL | cp LOCAL [USER@]NAME:REMOTE
                       copy files or directories from/to a worker
  builder NAME         print a Nix builders line for the worker
  setup nix NAME [--no-cache] [--no-auth] [--auth-host HOST] [--dry-run]
                       get the worker ready to use this host's Nix: the S3
                       cache and the access-tokens for private inputs
  setup niks3-token NAME [--force]
                       reissue a worker's short-lived niks3 push token
  setup register-log-file NAME JOB --log PATH
                       make an existing worker log available as a job
  setup netbird NAME | setup tailscale NAME
                       start or restart mesh access on a CI worker
  nix-cache NAME [--dry-run]
                       the cache part of setup nix
  completions zsh|bash print the shell completion script
  tui [VIEW] [-n SECONDS]
                       interactive terminal UI: the workers, their jobs and
                       logs, and the actions on them

Workers this host did not create (nixbot's pool, other hosts' ad-hoc
workers) are looked up on the control host on first use; you log in as
yourself there, as agent on your own ad-hoc workers.

Environment: RWORKER_HOST (default rofl-10), RWORKER_KEY (public key file,
default ~/.ssh/id_ed25519.pub), RWORKER_USER (SSH user override),
RWORKER_ICONS=0 (no Nerd Font glyphs for the agent),
RWORKER_AWS_CREDENTIALS_FILE (AWS profiles for nix-cache), NO_COLOR.

Short options may be grouped, for example: __ME__ ls -Aw.
